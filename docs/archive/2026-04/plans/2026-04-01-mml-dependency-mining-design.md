# MML 命令依赖关系挖掘系统 — 技术设计

> 状态：已根据 Codex v2 审查意见修订（v3）
> 日期：2026-04-02
> 修订说明：统一"高置信度"产品语义为"自动通过初筛"；新增 MVP 范围界定；插件拆分延后到功能稳定后；补充验收指标与治理原则

## 1. 问题定义

从现网 MML 脚本中挖掘命令参数间的索引依赖关系，构建参数级精确映射的命令依赖图谱。

**示例**：`ADD APN` 的参数 `VRFNAME` 依赖于 `ADD VPN` 的参数 `VPN`。

### 1.1 核心约束

- 已知依赖关系存储在数据库中，需增量补充未知依赖
- 脚本量级：万级命令（内存可处理）
- 目标粒度：参数级精确映射（命令A.参数X → 命令B.参数Y）
- 运行模式：持续增量挖掘
- 人工参与：高置信度自动通过初筛（仍需人工终审），中/低置信度分别经 LLM 辅助或直接进入人工审核
- 所有图谱入库操作可追溯、可撤回、可迭代
- LLM 集成作为通用基础设施，可复用于其他图谱提取任务

### 1.2 已确认的设计决策

| 决策项 | 结论 |
|--------|------|
| 已知知识存储形式 | 数据库表 |
| 依赖作用域粒度 | vendor + ne_type + version（最细） |
| 命令标识 | operation + name 不可分割，如 `ADD APN` |
| 脚本归属识别 | 导入时已绑定网元版本（复用 ne_version 表） |
| 脚本命令顺序 | 现网成功脚本，定义方一定在引用方之前 |
| LLM 工作流 | 先简后繁（单步调用 → 多步 workflow） |
| 噪声过滤 | 可插拔迭代，初始版宽松，后续根据数据调优 |
| 解析器策略 | 重新设计解析器，支持多行/引号/转义，作为一期前置 |
| 插件边界 | 独立 `mml_graph` 插件，通过共享数据库与 mml_manager 协作 |
| 候选统计单位 | 按脚本去重，候选主键为 (scope, ref_cmd, ref_param, def_cmd, def_param) |
| 状态模型 | 两层独立状态机：候选生命周期 + 图谱边生命周期 |

### 1.3 范围界定

#### 本方案要解决的问题

1. **输入可信性**：把现网 MML 脚本稳定解析成可计算的命令实例
2. **依赖发现**：从脚本中自动发现参数级依赖关系，减少人工手工整理
3. **依赖治理**：候选审查、人工确认、变更日志、撤回、追溯，避免图谱污染
4. **持续演化**：版本继承、周期复核、增量更新

#### 本方案不解决的问题

- 不替代 MML 命令文档的官方权威解释
- 不处理跨 vendor 的依赖关系泛化
- 不构建通用的知识图谱查询引擎

#### MVP 范围（第一期交付底线）

MVP 的目标是**验证依赖挖掘的业务价值**，只包含验证需求的最小闭环：

| 包含 | 不包含（延后到后续分期） |
|------|--------------------------|
| 解析器增强（多行、引号、转义） | 独立 `mml_graph` 插件骨架（MVP 阶段在 `mml_manager` 内实现） |
| 候选生成 + 多维评分 + 去重 | LLM 集成（第二期） |
| 人工审核队列 + 确认/拒绝 | 图谱变更日志 + 撤回机制（第二期） |
| 基础 API（候选列表、确认、拒绝） | 前端完整视图（第二期） |
| 最小前端界面（候选列表 + 操作） | 版本冷启动 + 已知边复核（第三期） |
| 4 张核心数据表 | 通用 LLM 调用层（第二期） |

**原则**：先验证"候选生成算法能否产出有价值的结果"，再投入平台化建设。

### 2.1 三层漏斗

- **代码层**：确定性的统计计算（快、便宜、可重复），过滤掉绝大多数噪声
- **LLM 层**：语义理解（读懂文档描述、判断参数含义），处理代码无法判断的模糊地带
- **人工层**：只处理 LLM 也没把握的少量疑难项

### 2.2 统一审核队列

- 所有候选（无论置信度）都进入同一个队列
- 区别只在于初始状态和审核路径：
  - 高置信度自动通过初筛，标记为 `auto_passed`，进入统一审核队列（仍需人工终审才入图）
  - 中置信度进入 `llm_review`
  - 低置信度进入 `man_review`
- 每条候选携带完整的推导依据（哪个脚本的哪行、值匹配分数、参数名相似度、共现频率）
- 前端可按置信度/状态筛选，支持批量操作
- 最终只有 `accepted` 状态才会触发图谱边的创建

### 2.3 变更日志

- 图谱每次变更都生成一条不可变日志记录
- 撤回不是"删除"，而是追加一条反向变更记录
- 支持按时间点回溯

## 3. 技术路线 — 算法流程

### 阶段 0：解析器增强（前置任务）

当前解析器仅支持单行正则匹配 + 逗号切分参数，存在明确的覆盖盲区。
依赖挖掘的所有后续阶段都建立在解析输出之上，因此解析器增强是一期的显式前置交付。

#### 3.0.1 当前能力边界

| 能力 | 状态 | 说明 |
|------|------|------|
| 单行命令解析 | 已支持 | `ADD APN: APN="test";` |
| 14 种操作类型 | 已支持 | ADD\|MOD\|DEL\|RMV\|SET\|GET\|LST\|DSP\|ACT\|DEA\|BLK\|UBL\|REG\|DEREG |
| 带引号参数值 | 部分支持 | 仅剥离外层双引号，不支持单引号、转义引号 |
| 参数无值（标志位） | 已支持 | `ADD APN: APN;` → value=None |
| 空行/注释跳过 | 已支持 | `//` 开头的行跳过 |
| 多行命令 | **不支持** | 命令跨行时被静默丢弃 |
| 值中逗号 | **不支持** | `DESC="a,b,c"` 被错误切分 |
| 块注释 | **不支持** | `/* ... */` 不识别 |
| 转义字符 | **不支持** | 值中的 `\"` 等转义不处理 |
| 解析失败报告 | **不支持** | 无法识别的行被静默跳过，无错误统计 |

#### 3.0.2 增强目标

1. **多行命令支持**：识别续行符（如行尾 `\` 或无分号时自动续行），合并后整体解析
2. **引号感知的参数切分**：在引号内的逗号不作为分隔符，支持双引号和单引号
3. **转义字符处理**：支持 `\"`、`\\` 等常见转义
4. **解析结果分类**：输出分为 `parsed`（成功解析）、`skipped`（注释/空行）、`unrecognized`（无法解析），提供解析健康度统计
5. **可选的严格模式**：严格模式下 unrecognized 行产生警告，宽松模式下静默跳过

#### 3.0.3 降级策略

当解析器遇到无法处理的输入时：
- 不抛异常，不中断流程
- 记录到 `parse_report`：`{total_lines, parsed, skipped, unrecognized, sample_unrecognized: [...]}`
- unrecognized 的命令不参与后续的候选生成
- 解析报告随脚本一起持久化，前端可查看

#### 3.0.4 验证要求

- 收集至少 20 条真实现网 MML 脚本作为回归测试集
- 测试集需覆盖：单行命令、多行命令、引号内逗号、转义字符、注释变体、混合格式
- 解析器增强后，现有 6 个 parser 测试必须全部通过（不回归）
- 解析报告的 unrecognized 率在真实脚本上应 < 5%

### 阶段 1：实例提取

```
输入: 一批 MML 脚本文件（已绑定 ne_version）
输出: 按作用域分组的命令实例集合

对于每个脚本:
  1. 解析 → 命令列表 [{operation, name, params, line_number}, ...]
  2. 作用域 = 脚本关联的 vendor + ne_type + version（已有绑定）
  3. 存储为命令实例:
     {
       script_id: "xxx",
       scope: {vendor: "huawei", ne_type: "UPF", version: "V100R005"},
       commands: [
         {index: 0, operation: "ADD", name: "VPN",
          params: [{name: "VPN", value: "vpn5g_01"}, ...]},
         {index: 1, operation: "ADD", name: "APN",
          params: [{name: "VRFNAME", value: "vpn5g_01"}, ...]},
       ]
     }
```

### 阶段 2：值匹配聚合

```
输入: 同一作用域下的所有命令实例
输出: 候选参数对 → 聚合统计

命令标识 = operation + name（如 "ADD APN"）

噪声过滤策略:
  · 初始版: 只排除 NULL 和空字符串
  · 后续迭代: 可插拔的值过滤器，支持配置规则
    - 短值、枚举值、纯数字等作为可配置过滤项
    - IP 地址、字符串不硬编码过滤（可能是真依赖）
```

#### 2.1 统计单位与去重规则

**候选聚合主键**：`(scope, ref_command, ref_param, def_command, def_param)`

所有统计指标均基于此主键聚合。同一主键下只存在一条候选记录。

**脚本级去重原则**：统计单位是"脚本"，不是"命中次数"。同一脚本内无论产生多少次值匹配，只计为 1 个贡献脚本。

**同脚本多次命中折叠**：
- 当同一脚本内 `cmd_i` 或 `cmd_j` 出现多次（如脚本中有 3 条 `ADD VPN` 和 2 条 `ADD APN`），
  同一参数对可能产生多组 `(value, line_def, line_ref)` 匹配。
- 折叠策略：按主键聚合时，同一 `script_id` 只贡献 1 次到 `hit_count`，
  但所有不同的匹配值都收录到 `hit_values`，所有行号对都收录到 `evidence` 中。

**反例抽样口径**：
- 反例 = 同时包含这两个命令、但目标参数对没有任何值匹配的脚本。
- 抽样方式：随机抽取，最多取 5 条。每条反例记录脚本 ID 和简要原因
  （如"两命令均存在但参数值无交集"）。

```
FOR EACH scope (vendor + ne_type + version):

  // 用于按主键收集去重后的脚本级数据
  accumulator = {}   // key: (ref_cmd, ref_param, def_cmd, def_param)

  FOR EACH script IN scope:

    commands = script.commands  // 按 index 有序
    script_hits = {}  // key: (ref_cmd, ref_param, def_cmd, def_param),
                      // value: set of matched values + list of (line_def, line_ref)

    FOR EACH (cmd_i, cmd_j) WHERE i < j:
      FOR EACH param_i IN cmd_i.params:
        FOR EACH param_j IN cmd_j.params:
          IF param_i.value == param_j.value
             AND value IS NOT NULL AND value != "":

            key = (cmd_j.op+"_"+cmd_j.name, param_j.name,
                   cmd_i.op+"_"+cmd_i.name, param_i.name)

            IF key NOT IN script_hits:
              script_hits[key] = {values: set(), lines: []}

            script_hits[key].values.add(param_i.value)
            script_hits[key].lines.append((cmd_i.line_number, cmd_j.line_number))

    // 同一脚本内，同一主键只记一次命中，但保留所有值
    FOR EACH (key, hit_data) IN script_hits:
      IF key NOT IN accumulator:
        accumulator[key] = {script_ids: set(), values: set(),
                            sample_lines: [], is_hit: True}
      accumulator[key].script_ids.add(script.id)
      accumulator[key].values.update(hit_data.values)
      accumulator[key].sample_lines.extend(hit_data.lines[:3])  // 每脚本最多3条行号对

  // 按主键生成候选
  FOR EACH (key, data) IN accumulator:

    total_scripts = 同时包含这两个命令的脚本总数

    candidate = {
      scope: scope,
      ref_command: key[0], ref_param: key[1],
      def_command: key[2], def_param: key[3],

      hit_count:       len(data.script_ids),    // 去重后的脚本数
      total_scripts:   total_scripts,
      hit_values:      list(data.values),        // 所有不同匹配值
      sample_scripts:  取 5 条代表性样例（含脚本ID、匹配值、行号）,
      counter_examples: 随机取 5 条反例脚本
    }
```

计算量评估：万级命令，单脚本内命令数/参数数都不大，单脚本毫秒级完成。

### 阶段 3：多维评分

对每个候选参数对计算四个维度：

#### 维度 1：支持度 (Support)

```
support = hit_count / total_cooccurrence_scripts

含义: 同时出现这两个命令的脚本中，有多少比例出现了值匹配

例: 487/510 = 0.954
95.4% 的共现脚本都出现了值匹配 → 强信号
```

#### 维度 2：值区分度 (Value Distinctiveness)

```
distinctiveness = unique_values / total_hits

含义: 匹配到的值中，有多少是唯一的
      唯一值越多 → 值本身具有标识性 → 更可能是依赖
      大量重复值（如都是"1"） → 可能是巧合

例: 450/487 = 0.924
92.4% 的值是唯一的 → vpn 名称天然具有区分度
```

#### 维度 3：顺序一致性 (Order Consistency)

```
order_consistency = def_before_ref_count / total_hits

含义: 定义方命令排在引用方之前的比例
      现网脚本先定义后引用 → 期望 ≈ 1.0
      如果显著 < 1.0，说明参数对可能方向反了

例: 487/487 = 1.0
```

#### 维度 4：参数名相关度 (Param Name Relevance)

```
初版: 字符串相似度
      · 编辑距离归一化
      · 子串包含检测
      · 去除常见前后缀后的比较（如去掉 NAME、ID 后缀）
后续演进: LLM 判断两个参数名是否语义相关

注: 此维度为辅助信号，不作为主判据
    很多真实依赖的参数名完全无关
```

#### 综合置信度

```
confidence = w1 * support
           + w2 * distinctiveness
           + w3 * order_consistency
           + w4 * name_relevance

权重可配置，初始建议:
  w1=0.35, w2=0.35, w3=0.20, w4=0.10

已知知识排除: 评分前查已知依赖库，已存在的参数对标记为 already_known，不进入候选
```

### 阶段 4：置信度分层 + 决策

#### 4.1 两层状态模型

本系统采用**两层独立状态机**，候选实体和图谱边实体各自维护状态，通过明确的转换规则关联。

**第一层：候选状态机**（候选记录的生命周期）

```
                          ┌──────────────────────┐
                          │      pending         │  ← 候选刚生成，尚未审核
                          └──────┬───────────────┘
                                 │
               ┌─────────────────┼──────────────────┐
               │ confidence      │ confidence        │ confidence
               │ ≥ θ_high        │ ∈ [θ_low, θ_high) │ < θ_low
               ▼                 ▼                   ▼
        ┌──────────────┐ ┌──────────────┐   ┌──────────────┐
        │ auto_passed  │ │ llm_review   │   │ man_review   │
        └──────┬───────┘ └──────┬───────┘   └──────┬───────┘
               │                │                   │
               │          ┌─────┴──────┐            │
               │          │ LLM 判定    │            │
               │          │ accept /    │            │
               │          │ uncertain   │            │
               │          └──┬─────┬───┘            │
               │             │     │                │
               │             ▼     ▼                │
               │     ┌─────────┐ ┌──────────┐      │
               │     │llm_     │ │man_      │◄─────┘
               │     │passed   │ │review    │
               │     └────┬────┘ └────┬─────┘
               │          │           │
               ▼          ▼           ▼
         ┌─────────────────────────────────┐
         │  人工最终裁定                     │
         │  (所有通过路径最终都需要人工确认)   │
         └──────────┬──────────────────────┘
                    │
            ┌───────┴───────┐
            ▼               ▼
     ┌────────────┐  ┌────────────┐
     │ accepted   │  │ rejected   │  ← 终态
     └────────────┘  └────────────┘
```

**候选状态定义**：

| 状态 | 含义 | 触发条件 |
|------|------|---------|
| `pending` | 刚生成，尚未分配审核路径 | 候选生成完成 |
| `auto_passed` | 统计置信度高，自动通过代码层 | confidence ≥ θ_high |
| `llm_review` | 等待 LLM 审核 | θ_low ≤ confidence < θ_high |
| `man_review` | 等待人工审核 | confidence < θ_low，或 LLM 返回 uncertain |
| `llm_passed` | LLM 审核通过 | LLM 返回 accept |
| `accepted` | 最终确认（终态） | 人工点击确认 |
| `rejected` | 最终拒绝（终态） | 人工点击拒绝 |

**关键规则**：
- `auto_passed` / `llm_passed` 只是中间态，**不直接生成图谱边**，仍需人工最终确认（可批量）
- 只有 `accepted` 状态才触发图谱边的创建或更新——这是平台的治理红线
- `rejected` 候选不生成边，记录保留用于审计和后续去重
- 候选状态一旦进入终态不可逆回（如需重新审核，生成新候选记录）
- **自动化只负责发现和分流，不直接替代最终治理责任**：入图必须有责任主体（人工确认人）

**第二层：图谱边状态机**（图谱边的生命周期）

```
     ┌──────────────────┐
     │     active       │  ← 当前有效的图谱边
     └──────┬───────────┘
            │ 撤回操作（人工触发）
            ▼
     ┌──────────────────┐
     │     revoked      │  ← 已撤回，保留历史
     └──────────────────┘
```

| 状态 | 含义 | 触发条件 |
|------|------|---------|
| `active` | 当前有效的依赖边 | 候选 accepted 时创建；或已有边更新 |
| `revoked` | 已撤回的依赖边 | 人工主动撤回，或复核不通过 |

**两层关联规则**：
- 候选 `accepted` → 创建新的图谱边（status=active），或更新已有边
- 候选 `rejected` → 不影响图谱边
- 图谱边 `revoked` → 边失效，但关联的候选记录状态不变（保留审计痕迹）
- 已撤销的边可通过新的 accepted 候选重新激活

#### 4.2 置信度分层

```
θ_high = 0.85 (可配置)
θ_low  = 0.50 (可配置)

自动通过 (confidence ≥ θ_high):
  · 支持度高 + 值区分度高 + 顺序一致
  · 状态 = auto_passed，进入统一审核队列
  · 前端标记"高置信度自动通过初筛"，可批量确认（仍需人工点击 accepted 才入图）

LLM 审核 (θ_low ≤ confidence < θ_high):
  典型场景:
    · 支持度中等（60-80%），需 LLM 看文档判断
    · 参数名完全不同，需 LLM 判断语义关联
    · 值区分度不够高，需 LLM 辅助分析

  LLM 输入:
    · 候选依赖 + 评分明细 + 代表性样例脚本
    · 可选: 关联的产品文档片段

  LLM 输出:
    · decision: accept / reject / uncertain
    · reasoning: 推理过程
    · confidence: LLM 自身置信度

  LLM=accept    → 状态 = llm_passed
  LLM=reject    → 状态 = rejected（终态）
  LLM=uncertain → 状态 = man_review（转人工）

人工审核 (confidence < θ_low, 或 LLM 转人工):
  前端展示:
    · 候选依赖 + 所有评分维度
    · 上下文脚本原文
    · LLM 的推理过程（如有）
    · 批量操作: 确认(accepted) / 拒绝(rejected)
```

### 阶段 5：现网核查

```
输入: 已确认的依赖关系集
核查库: 更大的现网脚本数据库

FOR EACH confirmed_dependency:
  在核查库中找到所有同时包含这两个命令的脚本
  检查: 引用方参数值 是否能在 定义方命令中找到匹配值

  result = {
    total_checked: 核查的脚本数,
    violations: 不满足约束的脚本列表,
    pass_rate: 通过率
  }

  IF pass_rate < 阈值 (如 95%):
    标记为"核查异常"，需人工复查
    (可能是挖掘出的依赖关系有误，或者是现网有配置错误)
```

### 阶段 6：版本冷启动与已知边复核

#### 6.1 版本冷启动策略

新版本脚本量不足时，系统无法独立挖掘出足够候选。采用以下继承策略：

**相邻版本继承**：
```
当某版本 V_new 的脚本数 < 最小样本阈值（如 20）时:

1. 查找相邻版本 V_prev（同 vendor + ne_type 的上一版本）
2. 从 V_prev 的 active 图谱边中提取所有依赖关系
3. 将继承的边标记为 source=inherited，confidence 取原值但加标记
4. 这些继承边进入 man_review 状态，需人工确认是否适用于新版本
5. 当 V_new 积累了足够脚本后，可触发独立挖掘，结果会覆盖继承的边
```

**继承规则**：
- 只继承 `active` 状态的边，不继承 `revoked` 或候选
- 继承边的新 confidence 在原值基础上乘以衰减因子（如 0.8），反映跨版本不确定性
- 继承边的 evidence 标注"来自版本 V_prev 的 N 个脚本"
- 一旦 V_new 有独立数据支撑，继承边的 confidence 被新计算的值替换

**最小样本阈值**：可配置，初始建议 20 条同时包含相关命令的脚本。

#### 6.2 已知边周期性复核

已有错误边会永久沉积，与"可撤回、可迭代"的承诺不一致。需要定期复核：

**复核触发条件**：
- 新批次脚本导入后，自动触发一次全量复核
- 也可由人工手动触发

**复核流程**：
```
FOR EACH active graph_edge:

  // 用当前全量脚本重新计算 support 和 distinctiveness
  new_scores = calculate_scores(edge, all_current_scripts)

  IF new_scores.support < 复核阈值（如 0.60）:
    标记为 "review_warning"
    进入复核队列，提示人工检查该边是否应撤回

  IF new_scores.support < 撤回阈值（如 0.30）:
    自动标记为 "review_critical"
    强烈建议撤回
```

**复核不自动撤回**：复核只产生警告和建议，撤回仍需人工确认。
复核结果记录到变更日志，包含旧分数和新分数的对比。

## 4. 数据模型

### 4.1 图谱数据模型

```
作用域 (Scope)
  └── vendor + ne_type + version

节点: 命令参数
  └── command = operation + name (如 "ADD APN")
  └── param (如 "VRFNAME")

边: 依赖关系
  └── ref: 引用方命令参数 (如 "ADD APN"."VRFNAME")
  └── def: 定义方命令参数 (如 "ADD VPN"."VPN")
  └── scope: 作用域
  └── confidence: 置信度分数
  └── source: 来源标签 (known | mined | llm_derived | human_confirmed)
  └── scores: 各维度原始分数
  └── evidence: 统计聚合 + 代表性样例
  └── status: active | revoked    ← 图谱边只有这两个状态
```

### 4.2 候选记录

```
候选 = 一次挖掘产出的待审核项

字段:
  · scope: 作用域
  · ref_command, ref_param: 引用方
  · def_command, def_param: 定义方
  · scores: {support, distinctiveness, order_consistency, name_relevance}
  · confidence: 综合分
  · status: pending | auto_passed | llm_review | man_review
            | llm_passed | accepted | rejected  ← 候选实体专用状态
  · evidence:
    · hit_count: 去重后的命中脚本数
    · total_scripts: 同时包含这两个命令的脚本总数
    · hit_values: 所有不同的匹配值列表
    · sample_scripts: [{script_id, lines, value}]（最多 5 条）
    · counter_examples: [{script_id, reason}]（最多 5 条）
  · review_history: [{action, reviewer, timestamp, comment}]
  · source_batch: 本次挖掘批次ID（支持按批次撤回）
  · graph_edge_id: 关联的图谱边ID（仅 accepted 状态有值）
```

### 4.3 变更日志

```
每条变更记录:
  · change_type: add | revoke | update
  · dependency_id: 关联的图谱边ID
  · candidate_id: 关联的候选记录ID
  · snapshot_before: 变更前快照 (JSON)
  · snapshot_after: 变更后快照 (JSON)
  · trigger: auto | llm | human
  · trigger_id: 操作者标识
  · created_at: 时间戳
```

## 5. LLM 集成设计

### 5.1 演进路线

```
V1（初始版）: 单步 LLM 调用
  · 结构化输入: 候选依赖 + 评分 + 样例
  · 结构化输出: accept/reject/uncertain + reasoning
  · 模板化的 prompt，支持不同任务类型

V2（演进版）: 多步 workflow
  · 步骤编排: 文档检索 → 语义判断 → 交叉验证 → 决策输出
  · 条件分支: 根据上一步结果决定下一步
  · 断点续跑: 保存中间状态
```

### 5.2 通用性设计

LLM 调用层作为独立服务，不绑定具体业务：
- 统一的 prompt 模板管理
- 统一的输入/输出 schema 定义
- 调用记录持久化（可追溯）
- 可复用于其他图谱提取任务

## 7. 测试与验证要求

### 7.1 解析器验证

- 收集至少 20 条真实现网 MML 脚本构建回归测试集
- 测试集需覆盖：单行/多行命令、引号内逗号、转义字符、注释变体、混合格式
- 现有 6 个 parser 测试必须全部通过（不回归）
- 真实脚本 unrecognized 率 < 5%

### 7.2 候选生成验证

- 构造包含已知依赖关系的测试脚本（如 `ADD VPN: VPN="x"; ADD APN: VRFNAME="x";`）
- 验证候选主键去重正确（同参数对只产出一条候选）
- 验证 `hit_count` 是去重后的脚本数，非命中次数
- 验证 `support`、`distinctiveness`、`order_consistency` 计算正确
- 验证已知依赖被正确排除

### 7.3 状态机验证

- 候选状态转换严格遵循两层状态机定义
- `accepted` 候选必须创建对应的图谱边（status=active）
- `rejected` 候选不创建边
- 已 active 的边被 revoke 后，边状态变为 revoked，候选记录不变
- 终态不可逆转

### 7.4 离线评估

- 需定义一组带标注的评估脚本（至少包含 20 条明确的依赖关系）
- 衡量指标：候选生成阶段的精确率、召回率、人工复核通过率
- 验证阈值 θ_high=0.85、θ_low=0.50 在真实数据上的有效性
- 评估结果记录到文档，作为后续阈值调优的依据

### 7.5 需求验收指标

| 指标 | 目标 | 说明 |
|------|------|------|
| 人工工作量下降 | ≥ 50%（相比纯手工整理） | 通过候选生成自动发现依赖，人工只需审核而非逐一查找 |
| 候选精确率（人工复核通过率） | ≥ 70% | `auto_passed` 候选中人工确认 accepted 的比例 |
| 候选召回率 | ≥ 80% | 已知依赖被成功挖掘为候选的比例 |
| 优先级策略 | 发现优先 > 入图保守 | 宁可多出候选让人工筛选，也不漏掉真实依赖 |

### 7.6 治理原则（平台红线）

以下原则作为平台治理的不可妥协红线，任何实现都不得绕过：

1. **自动化只负责发现和分流，不直接替代最终治理责任**
   - `auto_passed` / `llm_passed` 均为中间态，不直接创建图谱边
2. **入图必须有责任主体**
   - 只有 `accepted` 候选才能创建/更新 `active` 图谱边，且必须记录确认人
3. **撤回优先于删除**
   - 错误边转为 `revoked`，不物理删除，保留完整历史与证据链
4. **新证据可以挑战旧结论**
   - 已有 `active` 边不是永久正确，支持周期复核、预警和重新审查
5. **平台先保证治理闭环，再追求自动化比例**
   - 审计、追溯、回滚、责任边界优先于"尽量少人工"
