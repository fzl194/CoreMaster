- 审查对象：`docs/plans/2026-04-02-mml-incremental-mining-design.md`

## 1. 审查背景

本轮复审针对 Claude 提交的增量挖掘设计文档 v2，重点确认上一轮指出的 3 个设计级 P1 是否收口：

- 主状态是否收敛为 `pending / graph / non_graph / rejected`
- 文件挖掘事实层是否统一
- 算法版本方案 A 是否真正落到汇总规则

我确认这 3 个方向在文档层面已经明显修正：`review_route` 被拆成独立字段，`candidate_contribution` 被重新定义为统一事实层，`active_algorithm_version` 也被引入用于汇总隔离。

但文档里仍残留一个会破坏正式知识层的数据删除问题。

## 2. 审查范围

- 设计文档：`docs/plans/2026-04-02-mml-incremental-mining-design.md`

## 3. 发现的问题

### P1：重挖流程仍可能删除 `graph` / `non_graph` 关系记录，破坏正式知识层的稳定性

- 证据：
  - 重挖流程第 3 步写明“删除零贡献候选（当前算法版本无任何文件支持的候选）”：`docs/plans/2026-04-02-mml-incremental-mining-design.md:262`
  - 该步骤没有限定只删除 `pending / rejected`，也没有排除 `graph / non_graph`
  - 同一文档前文又明确说明：
    - `graph` / `non_graph` 是决策层状态：`docs/plans/2026-04-02-mml-incremental-mining-design.md:50`
    - 文件事实层与决策层应分离：`docs/plans/2026-04-02-mml-incremental-mining-design.md:27`
- 影响：
  - 如果某条关系当前已经是 `graph` 或 `non_graph`，而当前激活算法版本下暂时没有贡献，第 4.2 节的删除逻辑会把这条正式知识记录一并删掉。
  - 这与管理员要求的“图谱边/非图谱边切换是独立决策层，不能因为挖掘结果变化就直接丢掉正式知识”冲突。
  - 也会让事实层和决策层重新耦合，导致回退、追溯和知识持久性失真。
- 建议修复：
  - 第 4.2 节的“删除零贡献候选”必须收窄范围，至少只允许删除仍处于候选池的临时关系，例如 `pending / rejected`
  - `graph / non_graph` 在零贡献时应保留关系记录，仅将当前激活算法版本下的汇总分数置零或标记“当前版本无支持”
  - 文档需明确“零贡献删除”与“正式知识保留”的边界规则

## 4. 测试缺口

- 后续实现测试必须覆盖：
  - `graph` 关系在重挖后当前版本零贡献时仍被保留
  - `non_graph` 关系在重挖后当前版本零贡献时仍被保留
  - 只有候选池内的临时关系才允许因零贡献被清理

## 5. 回归风险

- 若不修正文档就直接实现，重挖逻辑容易把正式图谱边或非图谱记录当成“无贡献候选”删除，造成正式知识资产丢失。

## 6. 建议修复项

- Claude 继续修订设计文档 v2，明确：
  - 零贡献删除仅适用于候选池临时关系
  - `graph / non_graph` 永不因零贡献被直接删除
  - 正式知识在零贡献场景下的展示与分数策略

## 7. 最终评估

v2 已经把上一轮 3 个设计级 P1 的主体方向修正到位，但仍未达到可开工状态。需要先修复“重挖误删正式知识层”这个残余 P1，再进入实现阶段。
