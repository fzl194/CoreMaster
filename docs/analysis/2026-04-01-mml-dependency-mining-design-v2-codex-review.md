### 3.1 中风险：文档对“高置信度是否自动确认”仍然自相矛盾

- 位置：
  - `docs/plans/2026-04-01-mml-dependency-mining-design.md:19`
  - `docs/plans/2026-04-01-mml-dependency-mining-design.md:129`
  - `docs/plans/2026-04-01-mml-dependency-mining-design.md:399`
  - `docs/plans/2026-04-01-mml-dependency-mining-design.md:422`
- 问题：
  - 前文仍写着“高置信度自动确认”。
  - 但状态机章节又明确写成 `auto_passed` / `llm_passed` 只是中间态，所有通过路径最终都需要人工确认，只有 `accepted` 才落边。
- 影响：
  - 如果按前者理解，系统目标是减少人工，把高置信度结果直接入图。
  - 如果按后者理解，系统目标是“自动分流 + 人工终审”，并不真正自动确认。
  - 这是产品语义冲突，不只是文案问题，会直接影响 API、前端按钮、审计责任和人力预估。
- 建议：
  - 只保留一种定义。
  - 如果真实需求是“任何入图都要人工背书”，就把“高置信度自动确认”改成“高置信度自动通过初筛”。
  - 如果真实需求是“高置信度可自动入图”，则需要单独定义自动入图的回滚策略与审计责任。

### 3.2 中风险：方案已从“依赖挖掘功能”扩张成“新插件 + 新解析器 + 新审核平台 + 通用 LLM 基础设施”

- 位置：
  - `docs/plans/2026-04-01-mml-dependency-mining-design.md:34`
  - `docs/plans/2026-04-01-mml-dependency-mining-design.md:35`
  - `docs/plans/2026-04-01-mml-dependency-mining-design.md:667`
  - `docs/plans/2026-04-01-mml-dependency-mining-design.md:681`
- 问题：
  - v2 设计已经把任务拆成：
    - 解析器重写
    - 独立 `mml_graph` 插件
    - 新表、新 API、新前端视图
    - 通用 LLM 调用层
    - 版本继承与全量复核
  - 每一项单独看都合理，但组合后已经明显超出“先验证依赖挖掘是否满足业务”的最小范围。
- 影响：
  - 实现周期、联调成本、测试面、回归风险都会显著放大。
  - 如果你的真实需求只是“尽快得到一版可用的依赖发现能力”，这个方案很可能过重。
- 建议：
  - 在文档里再加一层“最小闭环”定义，明确哪些是验证需求必需，哪些是平台化增强。
  - 更稳妥的切法是：
    - MVP：解析增强 + 候选生成 + 人工确认入库
    - Phase 2：LLM 辅助
    - Phase 3：冷启动 / 复核 / 独立插件化
  - 如果插件边界不是硬约束，`mml_graph` 可以延后到功能稳定后再拆。

## 10. 需求对齐说明

基于用户补充的目标“直接建设一套长期可治理的依赖图谱平台”，当前方案的总体方向是匹配的。为了避免后续继续在实现中漂移，这里把“方案到底在解决什么”和“建议坚持的治理原则”明确写出。

### 10.1 当前方案要解决的核心问题

该方案本质上不是单纯做一个依赖发现算法，而是在建设一套“依赖发现与治理系统”，核心解决四类问题：

1. **输入可信性问题**
   - 需要把现网 MML 脚本稳定解析成可计算的命令实例，否则后续所有候选、评分、证据都会失真。

2. **依赖发现问题**
   - 需要从海量脚本中自动发现“命令 A 的参数 X 依赖命令 B 的参数 Y”这类参数级关系，而不是依赖人工手工整理。

3. **依赖治理问题**
   - 发现出来的依赖不一定都对，因此必须具备候选审查、人工确认、变更日志、撤回、追溯能力，避免图谱污染。

4. **持续演化问题**
   - 新版本会冷启动，旧依赖会过时，所以平台必须支持版本继承、周期复核、增量更新，而不是一次性导入后静态不变。

### 10.2 当前方案如何解决这些问题

- **解析器前置增强**：解决“输入不可靠”。
- **候选生成 + 多维评分**：解决“怎么从脚本里发现疑似依赖”。
- **候选状态机 + 图谱边状态机 + 变更日志**：解决“怎么把候选纳入可治理流程”。
- **版本冷启动继承 + 已知边复核**：解决“新版本数据不足”和“旧边长期失真”。

换句话说，当前方案试图把“脚本事实”逐层转成“候选依赖”，再转成“受治理的图谱边”，并且允许后续被新证据修正。

### 10.3 在长期治理目标下建议明确的治理原则

如果目标是长期可治理的平台，而不是短期自动出结果，建议文档后续明确采用以下治理原则：

1. **自动化只负责发现和分流，不直接替代最终治理责任**
   - 高置信度候选可以 `auto_passed`，LLM 可以 `llm_passed`，但是否入图应由人工 `accepted` 决定。

2. **入图必须有责任主体**
   - 图谱边一旦成为 `active`，应能追溯到对应候选、审查记录和最终确认人。

3. **撤回优先于删除**
   - 错误边不应物理删除，而应转为 `revoked`，保留完整历史与证据链。

4. **新证据可以挑战旧结论**
   - 已有 `active` 边不是永久正确，应允许周期复核、预警和重新审查。

5. **平台先保证治理闭环，再追求自动化比例**
   - 在长期平台目标下，审计、追溯、回滚、责任边界要优先于“尽量少人工”。

### 10.4 与当前文档仍需继续统一的点

虽然方向已匹配“长期治理平台”，但文档仍需进一步统一以下产品语义：

- 到底使用“高置信度自动确认”还是“高置信度自动通过初筛”这一套说法。
- 是否明确规定：**只有 `accepted` 候选才能创建/更新 `active` 图谱边**。
- 是否把“人工终审”定义为平台治理红线，而不是可选策略。

如果后续文档把以上三点写死，当前方案就会从“架构方向正确”进一步提升为“治理语义也完整闭合”。
