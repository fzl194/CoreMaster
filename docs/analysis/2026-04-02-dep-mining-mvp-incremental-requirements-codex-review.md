# Codex 复审结论：dep-mining-mvp-001 与增量挖掘新需求不匹配

- 状态：已审查
- 审查日期：2026-04-02
- 审查分支：`master`
- 审查版本：`fdea494`
- 审查对象：Claude 针对首轮 3 个 P1 的修复，以及管理员新明确的业务需求
- 关联文档：
  - 首轮审查：`docs/analysis/2026-04-02-dep-mining-mvp-codex-review.md`
  - Claude 修复报告：`docs/handoffs/2026-04-02-dep-mining-mvp-claude-fix.md`

## 1. 审查背景

Claude 已修复首轮审查指出的 3 个 P1 问题：引号内块注释误删、重新生成覆盖人工终态、前端按钮未先做提取。我确认这些修复方向本身是合理的。

但管理员随后进一步澄清了目标并非“按版本全量提取 + 全量生成”，而是“按文件选择的增量式挖掘系统”：

- 管理员手动选择若干文件参与挖掘
- 每个文件存在可替换的挖掘结果，文件会被标记为“已挖掘”
- 同一文件重挖时，应撤销该文件旧贡献并以新结果替换，而不是把汇总结果再累加一遍
- 候选池是长期汇总池，后续可继续追加新的文件批次并重新排序
- 已入图谱的边不再进入候选池，但可继续关联新证据
- 除图谱外，还需要“非图谱库”，表示专家确认绝不可能成为图谱边的关系
- `reject` 仅表示本次候选拒绝；`non_graph` 表示知识级否定，两者不能混用
- 图谱边和非图谱边都可回退到待审核，但 `non_graph` 不能直接转成 `graph`

基于这组新需求，当前实现即使修复了首轮 3 个 P1，仍然与目标系统模型不一致。

## 3. 发现的问题

### P1：当前实现仍是“按网元版本全量重跑”，不是“按文件增量挖掘”

- 证据：
  - 新增的批量提取接口会直接扫描某个 `ne_version` 下全部文件并重建 `command_instance`：`backend/plugins/mml_manager/main.py:679`
  - 生成接口仍然是按 `ne_version_id` 读取全部 `command_instance` 后统一生成候选：`backend/plugins/mml_manager/main.py:736`
  - 前端按钮现在只是把“先全量 batch extract，再全量 generate”串起来：`frontend/src/views/plugins/DependencyMining.vue:253`
- 与新需求的冲突：
  - 管理员要求的是“可选择若干文件挖一下”，不是“当前版本全部文件重跑一遍”。
  - 当前实现没有“本次选择了哪些文件参与挖掘”的边界。
- 建议修复：
  - 先补设计文档，定义“文件级挖掘任务 / 文件级结果 / 汇总更新”模型，再决定接口与表结构。

### P1：缺少“文件级挖掘结果”与“文件贡献替换”层，无法支持单文件重挖替换旧贡献

- 证据：
  - 当前持久化层只有 `command_instance` 和汇总后的 `dependency_candidate`，没有保存“某文件对某候选贡献了什么证据”的独立关系层：`backend/plugins/mml_manager/main.py`
  - 同一文件重挖时，只是删除并重插该文件的 `command_instance`；随后候选按全量命令重新计算，没有显式的文件级贡献撤销/替换机制。
- 与新需求的冲突：
  - 管理员明确要求“这个文件重新挖掘的话，这个文件对应的结果会更新，汇总结果也会更新，而不是汇总结果又直接增加一遍”。
  - 没有文件级贡献层，就无法可靠表达“撤销旧贡献、并入新贡献”。
- 建议修复：
  - 设计上至少增加“文件挖掘运行记录”和“文件对候选的贡献记录”两层，不要求首版就做最细证据仓，但必须能表达替换。

### P1：当前只有“候选 / 已接受 / 已拒绝”一套状态，不满足“图谱库 / 非图谱库 / 候选池”三层模型

- 证据：
  - 候选状态仍然是 `accepted` / `rejected` / 算法状态混在同一张 `dependency_candidate` 表中：`backend/plugins/mml_manager/main.py:90`
  - 接受后写入 `graph_edge`，但没有“非图谱库”概念，也没有对应状态流转或回退接口：`backend/plugins/mml_manager/main.py:795`
- 与新需求的冲突：
  - 管理员明确区分：
    - `reject`：本次候选不通过，后续可能因新证据重新进入候选池
    - `non_graph`：专家确认绝不可能成为图谱边，属于正式知识库
  - 并要求：
    - `graph -> pending`
    - `non_graph -> pending`
    - `non_graph` 不能直接转 `graph`
- 建议修复：
  - 重新设计状态机，不要继续把“审核结果”和“知识归档结果”混在一个枚举里。

### P1：当前模型没有表达“存量图谱与新增挖掘共用一套系统，但已入图谱边不再进入候选池”

- 证据：
  - 当前 `accept` 只是把候选同步到 `graph_edge`，并没有定义当新文件再次挖出同一 key 时应如何“追加证据到已有图谱边而非回到候选池”。
  - 当前保留 `accepted` 状态只是避免被后续 generate 覆盖，并未实现“候选池外的知识层累积证据”。
- 与新需求的冲突：
  - 管理员要求存量图谱和新挖掘是一套通用系统。
  - 已存在图谱边不应再进入普通候选队列，但应能关联新增证据；必要时还应能转回候选视角查看分数。
- 建议修复：
  - 在设计文档中明确“关系主键、候选池、图谱库、非图谱库、证据归属”的统一模型。

## 4. 测试缺口

- 当前新增测试仅覆盖“全量 batch extract + generate”场景，没有覆盖“选择部分文件增量挖掘”。
- 没有覆盖“文件重挖替换旧贡献”的测试。
- 没有覆盖“graph / non_graph / pending / rejected”状态机测试，因为当前实现根本没有这套模型。

## 5. 回归风险

- 如果继续在当前“按版本全量重跑”的模型上累加需求，后续再改成文件级增量模型时，表结构和接口会出现二次返工。
- 如果不先把 `reject` 与 `non_graph` 分开，后续专家知识沉淀会和普通审核意见混淆。
- 如果不单独建文件级贡献层，未来很难解释某条候选分数由哪些文件贡献而来，也很难支持可审计的重挖替换。

## 6. 建议修复项

- Claude 暂停在现有实现上继续打补丁，先补一份新的正式设计文档。
- 设计文档至少明确：
  - 文件级挖掘任务与“已挖掘”标记
  - 文件级结果 / 文件级贡献如何建模
  - 候选池如何做增量汇总与重挖替换
  - `graph` / `non_graph` / `pending` / `rejected` 的状态机
  - 存量图谱如何导入，并如何接收新证据
  - 未来算法版本升级后，文件“是否需要重挖”的管理方式

## 7. 无法确认的残余风险

- 管理员提到“算法版本字段变化如何管理”尚未完全定稿，因此新设计文档中需要给出至少一版可落地的版本管理方案。
- 当前尚未讨论“图谱边转回候选后分数如何展示”的精确定义，设计文档需要明确是复算还是读取汇总快照。

## 8. 管理员介入影响

- 本轮审查结论直接受管理员新澄清的业务需求影响。
- 该需求澄清改变了系统边界定义，因此当前结论不是“Claude 修复无效”，而是“Claude 修复了旧问题，但旧设计本身已经不足以承载新目标”。

## 9. 最终评估

当前 `fdea494` 可以视为“修复了首轮 3 个 P1 的补丁版”，但不能视为符合管理员新需求的目标实现。下一步应由 Claude 基于新需求重新输出设计文档，再进入下一轮实现，而不是继续在现有“按版本全量提取 + 全量生成”的模型上增量打补丁。
